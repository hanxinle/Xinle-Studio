## 旧方案：帧率定时器 + 声卡自然走速

### 工作原理

```
解码线程(全速):
  视频包 → 解码 → RGBA → 帧队列(上限 60)
  音频包 → 解码 → 重采样 S16 → 写入 QAudioSink(200ms 缓冲, 写满则阻塞重试)

主线程:
  QTimer(1000/fps 毫秒) → 每次从帧队列弹一帧 → GLWidget 显示
```

音频节奏靠 QAudioSink 的 200ms 缓冲写满后阻塞写入来"自然"维持；视频节奏靠一个按标称帧率设置的 QTimer。两条节奏链互不相干。

### 为什么它大部分时候很流畅

- 声卡消费 PCM 是严格匀速的，阻塞写入天然把音频解码速度钳在实时速率上。
- 常见视频帧率恒定（25/30fps），标称帧率定时器与真实 pts 间隔偏差很小。
- 帧队列（60 帧 ≈ 2 秒）吸收了编解码和定时器的抖动。
- 经过多轮迭代（部分写入重试、队列满时保留包不丢参考帧、循环播放处理等），边界情况大多被磨平。

### 瑕疵从哪来

两条独立时钟长期运行必然漂移，这就是"偶尔能感受到的瑕疵"：

1. **漂移**：QTimer 实际间隔 ≠ 帧真实 pts 间隔（定时器精度、帧率抖动、VFR 视频），累积几分钟后音画逐渐错位，且没有机制回正。
2. **seek 后旧音频残留**：seek 只动了 FFmpeg 侧，声卡 200ms 缓冲里积压的旧音频会继续放出来，音画短暂错乱。
3. **暂停/恢复**：声卡缓冲内容不暂停感知，恢复时先把旧缓冲放完才接上。
4. **打开第二个文件**：依赖 QThread 中断标志重启线程，标志不清除导致线程秒退（这个是后来修复时才发现的旧坑）。

### 评价

适合演示和轻量播放：实现最简、无锁竞争少、绝大多数内容看起来没问题。但它"流畅"是队列够深 + 内容规整撑起来的，不是机制保证的。

## 新方案：音频主时钟 + 按 pts 取帧

参考夏曹俊《FFmpeg 4.2 从基础实战》第十章的方案，映射到 Qt 技术栈。

### 核心原理

**音频做主时钟**：声卡匀速消费音频，主时钟就是"声卡实际播到哪了"；视频帧携带 pts 入队，取帧时与主时钟比较——太早等，太晚丢，到点显示。

```
主时钟 masterClock() = m_audioClockBase + QAudioSink::processedUSecs() / 1e6
```

`processedUSecs()` 返回声卡实际已播放的微秒数，等价于旧课程方案里"SDL 回调中队列头 pts + 墙钟推算已播放时长"，`suspend` 期间停走，**暂停补偿天然成立**。

### 取帧决策（getDisplayFrame，10ms 精确定时器驱动）

```
if 队头帧.pts > 主时钟 + 5ms   → 未到显示时间, 等待
if 队头帧.pts < 主时钟 - 80ms  → 严重过期, 丢弃并继续检查下一帧(追帧)
否则                           → 到点, 取出显示
```

### 关键状态切换

| 操作 | 动作 |
|------|------|
| seek | avformat_seek + flush 双解码器 + 清帧队列 + `resetAudioOutput()` 清空声卡积压 + 时钟基准 = 目标位置 |
| 暂停/恢复 | `QAudioSink::suspend/resume`，`processedUSecs` 停走/续走，时钟自动正确 |
| 播完循环 | 基准归零，发 `audioResetRequested` 信号由主线程重置声卡 |
| 打开文件 | `grabFirstFrame()` 同步解出首帧做封面，随后 seek 回文件头 + flush 解码器 |
| 无音频流 | 退化为旧方案的定时器逐帧显示 |

### 踩过的坑（复现必读）

1. **QThread 中断标志 restart 不清除**：`requestInterruption()` 设置的标志在 `start()` 重启后依然有效，第二次启动的 `run()` 会立刻退出。线程退出判断必须用自定义标志（`m_running`）。
2. **时钟基准要随文件关闭归零**：`close()` 里漏清 `m_audioClockBase` 的话，上个文件 seek 过的残留基准会让新文件所有帧被判为"过期"而丢光。
3. **QAudioSink 属于主线程**：重置声卡（stop+start）必须在创建它的线程做，解码线程需要重置时通过 Qt 信号转交主线程。
4. **不要用 `reset()`**：suspend 状态下 `reset()` 可能恢复不了，用 stop+start 彻底重置。

## 两代方案对比

| 维度 | 旧方案 | 新方案 |
|------|--------|--------|
| 同步机制 | 无，两条独立节奏链 | 音频主时钟，视频对齐 pts |
| 长期漂移 | 会累积，无回正 | 每 10ms 对齐一次，不累积 |
| seek 后 | 旧音频残留几百 ms | 声卡清空，立即从新位置起播 |
| 暂停恢复 | 先放完旧缓冲 | 时钟停走，无缝衔接 |
| 追帧能力 | 无 | 过期帧丢弃追帧 |
| 进度条 | 跟视频帧 pts，跳动感 | 跟主时钟，平滑 |
| 实现复杂度 | 最简 | 中（一个时钟函数 + 取帧决策） |

## 结论

新方案是当前最优实现，机制上消除了旧方案的漂移和 seek/暂停瑕疵。旧方案作为"最简可工作"的版本依然值得参考：它的背压设计（队列满保留包、声卡写满阻塞重试）被新方案完整继承。
